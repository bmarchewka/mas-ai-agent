# mas-agent Workflow

This skill defines the end-to-end mas-agent extraction pipeline **and** explains how
to turn it into a task list you can execute step by step. It is agent-agnostic — the SKILL.md format
is shared across IBM Bob, Claude Code, and similar tools, so the same file works everywhere.

All work is driven by `config.yaml` and the shell scripts in `scripts/` (see `AGENTS.md` for the
full file map).

## How to run

1. Present the steps below as a task list / checklist — one item per numbered step, in order — using
   whatever task-tracking mechanism your tool provides (a native task/plan capability or a plain
   markdown checklist).
2. Execute each step in sequence by running its script in `scripts/`. Each step depends on the
   output of the previous ones, so do not skip ahead.
3. After each step completes, print the summary table specified for that step.
4. While scaffolding the task list (before execution), do not modify any project files.
5. Step 2 runs once per operator tag in `catalog.operators`; steps 3–4 run once per resolved
   (tag, version) and write `MANAGE/<tag>/manage-<version>/` and `MANAGE/<tag>/core-<version>/`.
   `MANAGE/DBSCHEMA/` (step 5) is shared, because it comes from the database.
6. Re-running is safe: create a fresh task list rather than trying to de-duplicate against a
   previous run.

## Workflow steps

1. **Validate prerequisites** — Check that the configured container engine (`container.engine` in `config.yaml` — `docker` or `podman`, default `docker`) is available on PATH (every workflow step runs through it), and that `yq` (mikefarah) or `python3` is available for reading/writing `config.yaml`, then run `scripts/prerequisites.sh`. After completion, always display results as a markdown table with columns: Tool, Status, Version.
2. **Resolve Manage and MAS core versions from the operator catalog (per operator tag)** — Parse `catalog.operatorImage` and `catalog.operators` from `config.yaml`. `catalog.operators` maps each operator catalog tag to two independent version lists: `manage` (Manage operator versions, package `ibm-mas-manage`, image `manageadmin`) and `core` (MAS core versions, package `ibm-mas`, image `graphite-configuration`). Each item is `latest` (newest stable version in the catalog's `defaultChannel`; also used when a list or the whole tag entry is empty), a channel (`9.2.x`, `9.2`, `9.3.x-feature` → newest selectable version in it) or an exact version (`9.2.4`). The legacy `catalog.operatorTag: [tag, ...]` form means `latest` for both lists. For each tag, pull `<operatorImage>:<tag>`, copy `/catalog/ibm-mas-manage/` and `/catalog/ibm-mas/` (OLM file-based catalog: `package.yaml` with `defaultChannel`, `channel-*.yaml` entries, `objects/<bundle>.yaml` with `relatedImages`) and resolve the lists with `scripts/catalog_resolve.py` (host `python3`, or a python container). When a bundle's `relatedImages` list the image it is used directly (`source: catalog`); older catalogs (e.g. `v9-250403-amd64`) and older patch bundles list only the operator images, and then the image digest pinned by the operator release is traced (`source: operator`; Manage: `ibm-mas-manage` → `ibm-mas-manage-primary-entity` → `ibm-mas-manage-ws` → `manageadmin`; core: `ibm-mas` → `ibm-mas-suite` → `ibm-mas-entitymgr` → `graphite-configuration`; one vars file is copied out of each image without running it, pulled operator images are removed again, results are cached in `tmp/image-trace/`, and the `cp.icr.io` entitlement login is needed). MAS core ≤ 9.0 (and early 9.1 pre-releases) ships no Graphite: such `core` items are skipped with a NOTE and recorded in `status.operators.<tag>.skipped.core` — not a failure; Manage 9.0 still gets its SMP and Graphite apps. An unknown item fails with the valid versions of its channel. Write `status.operators.<tag>.catalogImage` and, per resolved version, `status.operators.<tag>.manage.<version>.{requested, channel, bundle, source, manageadmin}` and `status.operators.<tag>.core.<version>.{requested, channel, bundle, source, graphite}`; items resolving to the same version are merged. The status block is rebuilt each run (tags no longer configured are dropped; a tag whose catalog cannot be read keeps its previous entry). A failing tag or item does not stop the others, but the script exits non-zero. `--tag <tag>` limits the run; `--list-versions` only prints the selectable versions of each catalog (config unchanged). Implemented in `scripts/mas-manage-resolve-image.sh`. After completion, always display results as a markdown table with columns: Metric, then one column per operator tag. Rows: Status, Catalog image, Manage (resolved versions with image builds; `via operator` when traced), Core (graphite) (resolved versions with Graphite builds, or `skipped`).
3. **Extract MAS Manage SMP folder (per tag and Manage version)** — For each tag and each version under `status.operators.<tag>.manage`, read its `manageadmin` image, create/reuse a container, and copy `/opt/IBM/SMP/` (via `<engine> cp`) into local `MANAGE/<tag>/manage-<version>/SMP/` (cleared first, so it is an exact mirror). Files are copied verbatim, including compiled `.class` files, which are kept exactly as shipped in the image. If another folder was already extracted from the identical image (same digest), copy it locally instead. Also writes the manifest `MANAGE/<tag>/manage-<version>/images.yaml`. `--tag <tag>` / `--version <version>` limit the run. Implemented in `scripts/mas-manage-SMP-extract.sh`. After completion, always display results as a markdown table with columns: Metric, then one column per `tag / manage version`. Rows: Status, Image, Container, Class files, Total files, Output directory.
4. **Extract Graphite (per tag and core / Manage version)** — Part A: for each tag and each version under `status.operators.<tag>.core`, read its `graphite` image and copy `/graphite/node_modules/@maximo` (via a `--rm` container named `mas-manage-graphite-<tag>-<version>`, or locally from another folder with the identical image) into `MANAGE/<tag>/core-<version>/GRAPHITE/node_modules/@maximo` (cleared first), plus the manifest `MANAGE/<tag>/core-<version>/images.yaml`. Part B: for each tag and Manage version, unzip all Graphite app ZIP files from `MANAGE/<tag>/manage-<version>/SMP/maximo/tools/maximo/en/graphite/apps/` into `MANAGE/<tag>/manage-<version>/GRAPHITE/apps/` (cleared first), one subdirectory per app named after the ZIP file (without `.zip` extension); this needs step 3. `--tag <tag>` / `--version <version>` limit the run. Implemented in `scripts/mas-manage-graphite-extract.sh`. After completion, always display two markdown tables with columns: Metric, then one column per `tag / version`. Part A rows: Status, Image, Container, Files copied, Output directory. Part B rows: Status, Source, Apps unzipped, Apps directory.
5. **Export Maximo DB schema (and selected table data) to MANAGE/DBSCHEMA/** — **Runs only when `masManage.export` is `true` in `config.yaml` (default `false`).** When it is false or absent, the script skips the whole step without touching the database, the container engine or `MANAGE/DBSCHEMA/`, exits successfully, and prints the summary table with rows: Status (`Skipped (masManage.export = false)`), Output directory. Otherwise: Parse `masManage.database` fields (type, host, port, name, username, password, schema) from `config.yaml` and connect to the database using the engine named by `masManage.database.type`. Supported engines: `mssql` (SQL Server), `db2` (IBM DB2), and `oracle` (Oracle) — the engines IBM Maximo / MAS Manage runs on. The tables whose DDL is exported are selected by `masManage.schemaTables` in `config.yaml`: `*` (or the key absent) exports every table and view, while a YAML list such as `[WORKORDER, ASSET, LOCATIONS]` (inline or block form) limits the export to those objects (matched case-insensitively). Reflect the schema with SQLAlchemy and write each selected table's `CREATE TABLE` DDL (columns, types, constraints, primary keys, foreign keys) plus its `CREATE INDEX` statements to `MANAGE/DBSCHEMA/tables/<TABLE_NAME>.sql`, and each view definition to `MANAGE/DBSCHEMA/views/<VIEW_NAME>.sql`. In addition, export full row DATA as CSV for the tables selected by `masManage.dataTables` (same forms as `schemaTables`: `*` for all tables, or a YAML list such as `[MAXRELATIONSHIP, WORKORDER]`; but absent or empty means no data export). Each table is streamed (so million-row tables are handled) to `MANAGE/DBSCHEMA/data/<TABLE_NAME>.csv` — one file per table, named after the table, with a header row and SQL `NULL` written as an empty field. Creates the output directories if absent. Runs inside a dedicated `python:3-slim` container that is automatically removed when the export completes — no local database client or SQL tooling required, only the configured container engine (`docker` or `podman`). On ARM hosts (e.g. Apple Silicon) the DB2 engine runs the container under `--platform linux/amd64` automatically because IBM's `ibm_db` driver has no ARM64 build. Implemented in `scripts/mas-manage-db-schema-export.sh`. After completion, always display results as a markdown table with columns: Metric, Value. Rows (when exported): Engine, Database, Schema, Tables exported, Views exported, Data tables exported, Output directory.
